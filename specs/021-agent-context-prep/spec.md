# Feature Specification: Agent Context Prep (`[context]`)

**Feature Branch**: `021-agent-context-prep`

**Created**: 2026-08-21

**Status**: Draft

**Input**: User description: "Context Prep (Global before): Run a global hook
that gathers project health (e.g., current branch, lint errors) and injects it
into the agent's initial prompt context before it even chooses a task."

## Feature Summary

Agents meet a Runefile through two surfaces: the MCP server (`rune mcp` /
`rune serve`), where every available non-private task is a callable tool, and
the `agent` executor, where a task body becomes the prompt handed to an
installed agent CLI. On both surfaces the agent starts blind — it knows the
task names and descriptions, but nothing about the *state* of the project
(current branch, dirty files, failing lint), and must burn tool calls
rediscovering it.

This feature adds one new task attribute, `[context]`, marking a single task
as the project's **context hook**. Rune runs that task at the moment an agent
session begins — before the agent chooses or runs anything — and injects its
captured output into the agent's context:

- For an MCP session, the output becomes the `instructions` field of the
  initialize result, the protocol's designated slot for context the model
  should have. Run once per session, at initialize.
- For an `agent`-executor task, the output is prepended to the prompt under a
  fixed delimiter. Run once per task invocation.

Context prep is strictly best-effort: it runs under a hard timeout, and any
failure degrades to a one-line notice — it can never block agent access or
task execution. Output passes through the existing secret mask and a size cap
before injection.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - MCP Agents Start Informed (Priority: P1)

A Runefile declares a `[context]` task that prints the current branch, dirty
files, and quick lint findings. An AI agent connects via `rune mcp`. Before
listing or choosing any tool, the agent's client receives that output as the
MCP server `instructions`, so the model already knows the project's state
when it plans its first action.

**Why this priority**: This is the reported feature request — context "before
it even chooses a task". MCP initialize is the only point that precedes tool
choice.

**Independent Test**: Serve a Runefile whose `[context]` task emits a known
marker string; initialize an MCP session and confirm the initialize result's
`instructions` contains the marker.

**Acceptance Scenarios**:

1. **Given** a Runefile with a `[context]` task, **When** an MCP session
   initializes (stdio or HTTP transport), **Then** the initialize result's
   `instructions` field contains the task's captured stdout.
2. **Given** a Runefile with no `[context]` task, **When** a session
   initializes, **Then** behavior is identical to today (no instructions
   injected by this feature).
3. **Given** a `[context]` task, **When** the MCP tool list is read,
   **Then** the context task is absent from the tool list regardless of
   `[private]`.
4. **Given** the context task prints a value of a masked environment
   variable, **When** the session initializes, **Then** the injected
   instructions show `***` in place of the secret, exactly as tool output
   masking behaves.

---

### User Story 2 - Agent-Executor Tasks Get a Context Prefix (Priority: P2)

A task using the `agent` executor is invoked. Rune runs the `[context]` task
first and prepends its output to the prompt, delimited so the model can
distinguish gathered state from the author's instruction:

```
## Project context (generated by Runefile [context] task)
<captured output>

## Task
<task body prompt>
```

**Why this priority**: The second of the two agent surfaces; same concept,
same hook, evaluated fresh per invocation because each invocation is a new
agent session.

**Independent Test**: Run an `(agent)` task with a stub provider that records
the prompt; confirm the recorded prompt is the delimited concatenation of
context output and task body.

**Acceptance Scenarios**:

1. **Given** a `[context]` task and an `(agent)` task, **When** the agent
   task runs, **Then** the provider receives the delimited context prefix
   followed by the task body prompt.
2. **Given** no `[context]` task, **When** an `(agent)` task runs, **Then**
   the provider receives the task body prompt unchanged (no empty headers).
3. **Given** the `(agent)` task is invoked twice, **When** project state
   changes between invocations, **Then** each invocation reflects the state
   at its own start (the hook runs per invocation).

---

### User Story 3 - Context Prep Never Blocks Work (Priority: P3)

The context task hangs (a slow linter) or fails (missing binary, not a git
repo). The agent surface proceeds without project context: the injected text
is replaced by a single notice line, Rune logs a warning to its own stderr,
and the session or task continues normally.

**Why this priority**: A best-effort informational feature must never become
an availability risk; a broken lint binary must not brick all agent access.

**Independent Test**: Point the `[context]` attribute at a task that sleeps
past the timeout; initialize an MCP session and confirm it succeeds within
the timeout budget with the fallback notice as instructions.

**Acceptance Scenarios**:

1. **Given** a context task that exits non-zero, **When** a session
   initializes or an agent task runs, **Then** the injected text is exactly
   one line naming the hook and stating that Rune proceeded without project
   context, and a warning is written to Rune's stderr.
2. **Given** a context task that exceeds the 10-second timeout, **When** it
   is invoked, **Then** the hook is killed, the same degrade path applies,
   and the session/task proceeds.
3. **Given** a context task that emits more than the size cap (8 KiB),
   **When** its output is injected, **Then** the output is truncated at the
   cap with a visible `[truncated]` marker appended.
4. **Given** a context task carrying an OS attribute that does not match the
   host, **When** an agent surface starts, **Then** the hook is silently
   skipped (treated as absent), consistent with OS availability semantics.

---

### User Story 4 - Authoring Errors Are Caught Statically (Priority: P4)

A Runefile author misuses the attribute — declares two `[context]` tasks,
puts `[confirm]` on the context task, or gives it a parameter without a
default. Rune's analyzer rejects the file with a diagnostic before anything
runs, and the LSP surfaces the same diagnostic in the editor.

**Why this priority**: Static validation is cheap here and prevents
confusing runtime behavior, but the feature works without it being rich.

**Independent Test**: Analyze fixture Runefiles for each misuse and confirm
each produces its specific diagnostic.

**Acceptance Scenarios**:

1. **Given** two tasks carrying `[context]` (including via imports), **When**
   the Runefile is analyzed, **Then** analysis fails with a diagnostic
   naming both tasks.
2. **Given** a `[context]` task also carrying `[confirm]`, **When** analyzed,
   **Then** analysis fails: the hook must run unattended.
3. **Given** a `[context]` task with a parameter lacking a default, **When**
   analyzed, **Then** analysis fails: the hook is invoked with no arguments.
4. **Given** a valid `[context]` task, **When** the Runefile is formatted,
   **Then** the attribute is preserved and formatted like other attributes.

---

### Edge Cases

- The context task remains invocable by name from the CLI (`rune health`)
  for debugging; `[private]` composes as usual and hides it from `--list`,
  but MCP tool exposure is denied by `[context]` itself, independent of
  `[private]`.
- A context task that fails *because the health check found problems* (e.g.
  `golangci-lint run` exiting non-zero on findings) follows normal task
  semantics — the task fails and the degrade path applies. Authors who want
  findings as context append `|| true` so the task succeeds with the
  findings as output.
- Dependencies and post-hooks of the context task run under normal task
  semantics, inside the same overall timeout budget.
- Output is captured from stdout only; stderr goes to Rune's stderr as
  usual.
- The 10s timeout and 8 KiB cap are fixed constants in this version; no
  configuration knob is introduced.
- Masking applies before truncation, so a secret spanning the cap boundary
  cannot leak through a truncated suffix.
- The MCP hook runs once per session at initialize; state changes during a
  long session are not reflected (accepted for this version; a refresh
  mechanism is explicitly out of scope).
- `[context]` on a task that is itself an `(agent)` task is rejected by the
  analyzer: the hook must not recursively require an agent session.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: A new task attribute `[context]` MUST mark a task as the
  Runefile's context hook; at most one task in the post-import task set may
  carry it, enforced by analysis with a diagnostic naming the offenders.
- **FR-002**: On MCP session initialize (both stdio and HTTP transports),
  the context hook MUST be run and its processed output returned as the
  initialize result's `instructions` field, once per session.
- **FR-003**: On each `agent`-executor task invocation, the context hook
  MUST be run and its processed output prepended to the provider prompt
  under the fixed delimiters `## Project context (generated by Runefile
  [context] task)` and `## Task`.
- **FR-004**: Hook output MUST pass through the existing secret-masking
  pipeline and then be truncated to 8 KiB with a `[truncated]` marker before
  injection on any surface.
- **FR-005**: The hook MUST run under a hard 10-second timeout. On timeout,
  non-zero exit, or any execution error, the surface MUST proceed with a
  one-line fallback notice in place of the context and a warning on Rune's
  stderr; context prep MUST NOT block session initialization or task
  execution.
- **FR-006**: A `[context]` task MUST NOT be exposed as an MCP tool,
  independent of `[private]`; it MUST remain invocable by name from the CLI
  and MUST respect `[private]` for listing surfaces as usual.
- **FR-007**: The analyzer MUST reject: more than one `[context]` task,
  `[context]` combined with `[confirm]`, `[context]` on a task with any
  parameter lacking a default, and `[context]` on an `agent`-executor task.
  The LSP MUST surface these diagnostics.
- **FR-008**: A `[context]` task whose OS attributes do not match the host
  MUST be treated as absent (silently skipped), per existing OS availability
  semantics.
- **FR-009**: When no context hook exists (or it is OS-skipped), agent
  surfaces MUST behave exactly as before this feature — no empty headers,
  no notices.
- **FR-010**: Documentation MUST cover the attribute in the Runefile
  language guide and the MCP guide, with a runnable example; the
  documentation test suite stays green.

### Non-Functional Requirements

- **NFR-001**: Parsing, formatting, and analysis of existing Runefiles that
  do not use `[context]` are byte-identical to today.
- **NFR-002**: The timeout and size cap are compile-time constants (10s,
  8 KiB) in this version; no new flags, env vars, or config file entries.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: With a `[context]` fixture, an automated MCP test observes the
  hook's marker output in the initialize result's `instructions` on both
  transports, and the context task absent from the tool list.
- **SC-002**: With a stub agent provider, an automated test observes the
  delimited context prefix in the prompt, and its absence (byte-identical
  prompt) when no hook is declared.
- **SC-003**: Fault-injection tests (non-zero exit, sleep past timeout,
  oversized output, secret in output) each produce the specified degrade,
  truncation, or masking behavior, and every such session/run still
  succeeds.
- **SC-004**: Analyzer fixtures for each authoring error (duplicate hook,
  `[confirm]`, defaultless parameter, agent executor) fail analysis with
  their specific diagnostics; a valid fixture passes and round-trips through
  the formatter unchanged.
- **SC-005**: `rune docs-check` passes with the new documentation and
  example.

## Assumptions

- MCP server `instructions` is the correct and sufficient client-side
  channel: mainstream clients (Claude Code, IDE integrations) append it to
  the model's system context. No per-tool description preamble or MCP
  resource is provided.
- Once-per-MCP-session freshness is acceptable; mid-session refresh, TTL
  caching, and a "refresh context" tool are out of scope until real usage
  demands them.
- The fixed 10s/8 KiB limits are adequate defaults; configurability is
  deferred.
- The context hook runs with the same environment and working directory as
  any directly invoked task; it is not sandboxed differently.
- Injecting context into non-agent surfaces (plain CLI runs, TUI) is out of
  scope — this feature is only about agent-facing context.
